# Трекинг скачек в реальном времени на 25 камерах и одном GPU

**Race Vision: система компьютерного зрения для определения позиций лошадей на скорости 38 FPS, RTX 3060**

---

## Аннотация

Мы разработали систему компьютерного зрения, которая в реальном времени отслеживает и идентифицирует 5 лошадей по 25 IP-камерам на ипподроме длиной 2500 метров — на одной потребительской видеокарте NVIDIA RTX 3060 (12 ГБ). Система определяет позиции в заезде: детектирует жокеев, классифицирует их по цвету экипировки и объединяет наблюдения с перекрывающихся камерных зон в единый рейтинг — всё за менее чем 26 мс на кадр. В статье описаны ключевые инженерные вызовы: одновременная обработка 25 видеопотоков, идентификация наездников при разрешении 30–100 пикселей и поддержание стабильной идентичности между камерами без нейросетей реидентификации.

## 1. Проблема

![Вид с камеры ипподрома с детекциями](../ds_results/exp2/frames/cam-05_batch00100.jpg)
*Рис. 1. Вид с одной камеры — 3 жокея детектированы и классифицированы по цвету в реальном времени*

Конные скачки — один из немногих крупных видов спорта без автоматического трекинга позиций. В отличие от футбола или Формулы-1, где GPS-трекеры и транспондеры давно стали стандартом, скачки до сих пор полагаются на комментаторов и фотофиниш.

**Почему это сложно?**

| Вызов | Детали |
|-------|--------|
| Масштаб | 2500 м трек, 25 камер, зоны перекрытия по 10 м |
| Скорость | Лошади движутся со скоростью 60 км/ч — пересекают поле зрения камеры за 2–3 секунды |
| Бюджет | Одна видеокарта (RTX 3060, 12 ГБ), а не дата-центр |
| Идентификация | 5 жокеев нужно различать в реальном времени только по цвету экипировки |
| Разрешение | На типичной дистанции от камеры жокей занимает 30–100 пикселей |

Цель: показывать зрителям живую таблицу позиций, обновляемую в реальном времени, через веб-браузер.

## 2. Архитектура

Система разделена на три полностью независимых конвейера, не имеющих общей синхронизации:

```
                            +--------------------------+
                            |   25 IP-камер (RTSP)     |
                            +--------+---------+-------+
                                     |         |
                    +----------------+         +----------------+
                    |                                           |
          +---------v----------+                    +-----------v---------+
          |  Аналитика         |                    |  Отображение        |
          |  (DeepStream C++)  |                    |  (go2rtc, 0% GPU)   |
          |                    |                    |                      |
          |  25 потоков @ 38fps|                    |  25 потоков WebRTC   |
          |  YOLO + Классиф.   |                    |  без транскодирования|
          |  Один GStreamer     |                    |                      |
          |  pipeline           |                    |                      |
          +---------+-----------+                    +-----------+---------+
                    |                                            |
             Shared Memory                                  WebRTC P2P
             (30 КБ, POSIX)                                      |
                    |                                            |
          +---------v-----------+                                |
          |  Python Backend     |                                |
          |  (FastAPI)          |                                |
          |                     |                                |
          |  SHM Reader ~1кГц  |                                |
          |  Vote Engine        |                                |
          |  Fusion Engine      |                                |
          |  WebSocket 10 Гц   |                                |
          +---------+-----------+                                |
                    |                                            |
                WebSocket                                        |
                    |                                            |
          +---------v--------------------------------------------v--------+
          |                        Frontend (React)                       |
          |                                                               |
          |   25x <video> (WebRTC)  +  <canvas> overlay (bbox + цвета)  |
          |   Независимые потоки      requestAnimationFrame 60fps        |
          +---------------------------------------------------------------+
```

**Ключевой принцип: каждый слой работает на своей скорости.** Аналитика обрабатывает кадры на 38 FPS. Python-бэкенд опрашивает shared memory на ~1000 Гц. WebSocket отправляет клиентам на 10 Гц. Фронтенд рендерит на 60 FPS. **Никто никого не ждёт.**

## 3. Детекция: найти жокея в 50 пикселях

![Кропы жокеев на разных дистанциях](../ds_results/exp2/crops/b00059_cam-05_t2_yellow_78x153.jpg) ![](../ds_results/exp2/crops/b00090_cam-05_t0_green_57x113.jpg) ![](../ds_results/exp2/crops/b00276_cam-05_t1_green_51x77.jpg)

*Рис. 2. Реальные кропы жокеев из пайплайна — 78x153, 57x113 и 51x77 пикселей. Именно с этим работает наш классификатор.*

### 3.1 Почему стандартные детекторы не работают

Модель YOLO, обученная на COCO, детектирует класс «person» — но на ипподроме «person» включает зрителей, судей, работников трека и жокеев. В наших тестах **более 60% детекций были не жокеями**: люди у ограждений, техперсонал.

Мы обучили кастомную YOLOv11s на специфичных для ипподрома данных. В сочетании с пространственной фильтрацией (ROI-маски для каждой камеры) процент ложных срабатываний снизился до менее 5%.

### 3.2 Ловушка разрешения

IP-камеры выдают 1920x1080, но мультиплексор NVIDIA DeepStream (nvstreammux) объединяет все 25 потоков в единое разрешение для GPU-инференса. При начальном разрешении mux 800x800:

| Объект | Размер в mux | Размер кропа |
|--------|-------------|--------------|
| Жокей + лошадь целиком | 24 x 49 пкс | — |
| Торс жокея (для определения цвета) | 14 x 15 пкс | 14 x 15 пкс |

**14 на 15 пикселей.** Даже человек не сможет надёжно определить цвет при таком разрешении.

Увеличение mux до 1920x1080 удвоило размер кропов до ~59x117 пкс в среднем — достаточно для надёжной классификации. При этом разрешение инференса YOLO остаётся 800x800 (nvinfer масштабирует автоматически), поэтому качество детекции не меняется, а кропы становятся значительно лучше.

## 4. Классификация цвета: путь проб и ошибок

### 4.1 Что мы пробовали (и почему не сработало)

Определить жокея по цвету экипировки звучит тривиально. Пять ярких контрастных цветов: синий, зелёный, красный, жёлтый, фиолетовый. Просто посмотри на доминирующий оттенок, да?

**Подход 1: HSV-гистограмма**
- Результат: **18.5% точности**
- Причина: зелёная поверхность трека и синие штаны жокея доминируют в кропе. Красный жокей распознаётся как «зелёный», потому что трава за ним занимает больше пикселей, чем его куртка.

**Подход 2: DINOv2 реидентификация**
- Результат: **17.7% идентифицировано** (82% — unknown)
- Причина: self-supervised эмбеддинги не могут сопоставить фото с телефона с 50-пиксельными кропами с камер видеонаблюдения. Совершенно разные визуальные домены.

**Подход 3: BoT-SORT ReID (предобученный)**
- Результат: **125 track ID** на 3 лошади (должно быть 3)
- Причина: модель ReID обучена на пешеходах MOT20. Жокеи верхом на лошадях — совершенно чужой домен. 50-пиксельный силуэт на лошади не похож на пешехода в городе.

**Подход 4: EfficientNet-классификатор (3 класса)**
- Результат: красный жокей классифицирован как зелёный. Жёлтый — как зелёный.
- Причина: обучен на 3 классах вместо 5. Маленький датасет. Кропы содержали слишком много лошади и фона.

### 4.2 Что реально сработало

Лёгкая кастомная CNN (5 свёрточных слоёв, вход 64x64, 5 классов), обученная на **725 тщательно отобранных кропах**, извлечённых непосредственно с тех же IP-камер.

| Цвет | Точность | Уверенность |
|------|----------|-------------|
| Зелёный | 100% | 95%+ |
| Красный | 100% | 90%+ |
| Жёлтый | 100% | 95%+ |
| Синий | 99% | 85%+ |

**Секрет:** обучающие данные с тех же камер, на которых работает система. Не ImageNet. Не картинки из интернета. Не фото с телефона. Модель выучила конкретный цветовой рендеринг, баланс белого, контраст и углы обзора именно наших камер.

Размер модели: **2.4 МБ**. Время инференса: **0.4 мс на кроп** на GPU.

## 5. Баги, которые научили нас больше всего

### 5.1 Пиксели не с той камеры

![Кадр с детекциями нескольких лошадей](../ds_results/exp2/frames/cam-05_batch00035.jpg)
*Рис. 3. Детекция нескольких лошадей — bounding box должен читать пиксели с правильной поверхности камеры*

На одной камере — 100% точность. На пяти камерах — точность упала до 45%.

Координаты bounding box были правильными. Модель классификатора была правильной. Но кроп **выглядел как пустое поле** вместо жокея.

Корневая причина: nvstreammux от NVIDIA собирает кадры камер в батч в произвольном порядке. `source_id` (индекс камеры, постоянный) — это не то же самое, что `batch_id` (позиция в текущем батче). Мы читали пиксели с поверхности Камеры 12, используя координаты bounding box Камеры 5.

**Исправление в одну строку. Недели отладки.**

### 5.2 NV12 — это не RGBA

Поверхности DeepStream используют цветовой формат NV12 (плоскость Y + чередующаяся плоскость UV). Наш CUDA-ядро для обрезки предполагало расположение памяти RGBA. Результат: каждый кроп представлял собой шумовой узор. Классификатор при этом выдавал уверенные предсказания — просто абсолютно неправильные.

### 5.3 Классификатор за 900 мс

Начальная реализация выделяла GPU-память (`cudaMalloc`) для каждого отдельного кропа на каждом кадре. При 150 кропах с 25 камер за батч из 50 кадров это создавало 150 циклов выделения/освобождения.

Предварительное выделение одного буфера и группировка кропов по камерам сократили время классификации с **900 мс до 340 мс** — ускорение в 2.7 раза только за счёт устранения накладных расходов на управление памятью.

## 6. Фьюжн с нескольких камер

Трек длиной 2500 м невозможно охватить одной камерой. Мы используем 25 камер с зонами перекрытия по 10 метров. Задача: объединить наблюдения в единый рейтинг.

```
Камера 1        Камера 2        Камера 3
[==========]
        [==========]
                [==========]
  перекрытие ↕    перекрытие ↕

Лошадь А: видна на позиции 450 м (кам. 1) и 455 м (кам. 2)
Лошадь Б: видна на позиции 460 м (кам. 2) только
→ Рейтинг: Лошадь Б лидирует, Лошадь А отстаёт на 10 м
```

Каждая камера независимо голосует за позиции жокеев. **Движок голосования на основе позиций** накапливает уверенность по нескольким кадрам, прежде чем зафиксировать результат. Только когда движок достигает порога уверенности (или таймаута), наблюдение камеры передаётся в **движок фьюжна**, который объединяет все камеры в глобальный рейтинг.

Это предотвращает искажение таблицы лидеров из-за ошибочной классификации на отдельном кадре.

## 8. Выводы

1. **Данные из целевого домена побеждают любую foundation-модель.** DINOv2, CLIP, предобученный ReID — всё провалилось. Крошечная CNN, обученная на 725 кропах с реальных камер, достигла 99%+ точности.

2. **Разделяйте Capture / Inference / Display.** Три независимых цикла с однослотовыми буферами между ними. Отображение никогда не ждёт инференс. Инференс никогда не ждёт захват. Один этот паттерн устранил все лаги интерфейса.

3. **Самые сложные баги — координатные.** Неправильный индекс поверхности, неправильное цветовое пространство, неправильная система координат — всё даёт «почти правильные» результаты, которые крайне сложно диагностировать.

4. **Потребительских GPU достаточно.** 25 камер, детекция + классификация + трекинг + фьюжн в реальном времени на видеокарте за $330. Узкое место — инженерия, а не железо.
